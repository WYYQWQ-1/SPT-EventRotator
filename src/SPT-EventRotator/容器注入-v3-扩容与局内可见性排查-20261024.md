## 3. “到局内就没了”的排查结论

### 3.1 已核实合法（逐条有出处）

| 项 | 结论 | 证据 |
|---|---|---|
| `Items[]._id` | 24 位 hex、全表唯一 | `NewHex24()`；探针断言「全为 24 位 hex / 全表唯一」0 违规 |
| `upd` | 只含 `StackObjectsCount`（可堆叠物按 `stacks`），**与 SPT 官方静态战利品同型**：官方 `CreateStaticLootItem` 只给 MONEY/AMMO 写 `Upd.StackObjectsCount`，其它一律 `Upd = null` | `LocationLootGenerator.cs:761-767`；探针断言 0 违规 |
| `slotId` | 逐字等于该容器 `_props.Grids[]._name`，从 `items.json` 读真名（不写死 `"main"`） | 探针断言 0 违规 + 把某容器格子改名成 `grid_custom` 后注入件跟着改名 |
| `location` | **v3 改为 postfix 自己算空格并写显式 `{x,y,r}`**（见 3.2） | 探针：整局 420 个容器、直接子物品 840 件，**非法坐标 0 / 越界 0 / 重叠 0** |
| `parentId` | 指向运行期 `Root`（SPT 每局会重写根 `_id`，已修） | 实机日志 `改 parentId 145 件` + 探针断言 |

### 3.2 `location` 为什么要显式给（不是“客户端会自己找”就完事）

客户端 `ItemFactory.FlatItemsToTree`（`audit/client_full/Assembly-CSharp.decompiled.cs:570091`）：

```csharp
LocationInGrid location = item2.location != null
    ? ItemDeserializer.CreateItemLocation<LocationInGrid>(item2.location)
    : grid.FindFreeSpace(value3);
error = grid.AddItemWithoutRestrictions(value3, location).Error;
```

`Grid.AddInternal` 第一句就是 `if (location == null) return new NoFreeSpaceError(...)`；而给了坐标时，
即使撞位也只走 `ignoreRestrictions` 分支（照样放进去，只多一行 error）。⇒ **显式坐标严格优于 null**。
所以 v3 在 postfix 里按「该格子现有原生战利品的真实占位 + 尺寸」算一个空格写进去；
算不出（真的塞满）才留 null，并**计数**：`…（白名单命中 N 个，格子算不出空格 K）`。
实机看到 `K>0` 就说明确实存在“没空格被客户端丢件”。

### 3.3 为什么“局内看不到”最可能是**开的箱子不在白名单里**

* 服务端数据是**真的存在**：实机 `spt20261024.log:7586-7589`（02:00 那局）
  `A total of: 1764 static items spawned` → `本局容器 307 个，含注入物件的容器 145 个，改 parentId 145 件`；
  探针在**同一份实机 staticContainers.json 副本**上把整套对象序列化成返回给客户端的 JSON，
  注入件的 `parentId / slotId / location` 都在里面。
* 原生战利品对格子的占用率（按 `staticLoot.json` 的件数分布 × 物品面积 ÷ 格子面积实测）
  只有 **18.5%～47.8%**（MedBag 18.5%、ToolBox 23.7%、SportBag 24.8%、WeaponCrate 29.8%、
  Drawer 22.1%、GrenadeBox 36.0%、barrel_cache 44.4%、wood_cache 47.8%）
  ⇒ “格子被塞满导致客户端丢件”**不可能**是普遍原因，最多零星几个。
* 02:00 那局的 **307 个容器里只有 145 个**在我们的白名单里（≈47%）。森林里数量最多、玩家最容易开的那几类
  —— 木制板条箱 57、PMC/scav 尸体 58、抽屉 36、埋藏桶/箱 45 —— **恰好全是当时没覆盖的**。
  玩家描述的“Salewa、钉子（管道胶带）”这类物品，实机分布里**既出现在白名单容器、也出现在抽屉/尸体/埋藏点**
  （`staticLoot.json` 反查：ducttape 5c06779c/57347c11 出现在 Drawer、scavDead、barrel_cache、wood_cache 等），
  所以「开了几个箱子全是原生内容」与「开的都是未覆盖容器」完全自洽。
* ⚠ 诚实边界：02:00 那局的**客户端日志已经不在**（现存 `Logs/log_2026.10.24_*` 只覆盖 09:58–10:16），
  所以「客户端有没有把某一件丢掉」这件事**仍缺一条实机日志**。v3 已经把能自证的东西都打进日志了：
  下一局对照 **注入明细 + 样例** 就能判断——如果开的类型出现在明细里却没有东西，
  那就去 `user/logs/log_*/errors.log` 找 `Item deserialization error: No free space…`（或
  `Could not add … to …`），把那一行发过来即可定案。
