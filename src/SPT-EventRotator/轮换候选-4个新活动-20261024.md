## 1. 原轮换规则（先查清，给 file:line）

### 1.1 `PickCore` 的候选池：`rotation.pool` 空 vs 非空

| `rotation.pool` | 行为 | 代码位置 |
|---|---|---|
| **空**（实机现状） | `all` 里取：`!IsSeasonal` **且**（`StartMonth <= 0` **或**（「未开季节轮换」且 `IsTaskEvent`）**或** `AlwaysInRotation`） | `Rotation.cs:257-277` → `CandidatePool()` `Rotation.cs:197-216` |
| **非空** | **白名单**：只从 `pool` 列出的 id 里选，**其它活动全部出局**；且这条路**绕过**日期窗与季节判断 | `Rotation.cs:252-256` |

> ⚠ 这正是用户警告的坑：`Pool.Count > 0` ⇒ **只轮这些**。若把 pool 写成只剩我们 4 个，
> 16 个老 `event_task` + 5 个 `reward` + 2 个老 AI 全部**永久退出轮换**（原有轮换直接废掉）。
> 所以本次**没有**用 pool（若一定要用，见 §8 的完整 24 个 id 清单，但会「冻结」候选池）。

### 1.2 `taskFollowsRealTime` 由什么决定（决定带日期窗的 `event_task` 能否进池）

```
Rotation.cs:251   bool taskFollowsRealTime = !IsRotatingSafe();
Rotation.cs:173-176  IsRotatingSafe() = SeasonRotation.IsRotating  （拿不到 ⇒ false ⇒ true，可降级）
SeasonRotation.cs:627  IsRotating => Mode == "rotate"
```

- 实机 `config.json`：`seasonRotation.mode = "rotate"` ⇒ `IsRotating = true` ⇒ **`taskFollowsRealTime = false`**
- ⇒ 判据 `StartMonth <= 0 || (!taskFollowsRealTime && IsTaskEvent(e))` 里后半段成立
  ⇒ **17 个 `event_task` 全部不看日期窗**（其中 `night_of_the_cult` 是往年变体 `yearVariant=true`，
  被 `PickCore` 的 v0.1.5 过滤剔掉 ⇒ 实际进池 **16 个**）。

## 3. 为什么是 `alwaysInRotation`，不是 pool、也不是「AI 全豁免」

| 方案 | 结果 | 为什么不用 |
|---|---|---|
| **A. `rotation.pool` 白名单（24 个 id 全抄）** | 行为等价 | ① 非空池 = **冻结**候选池：以后新增活动/改日期窗**不会**自动进池；② 实机 `config.json` 是用户自己的，打包原样带走 ⇒ 改工作区模板**不生效**，得让用户手改配置；③ 这条路**绕过**季节/日期窗判断，语义漂移 |
| **B. 代码里把 `event_task` 的豁免复制给 `event_ai`** | 22 个带窗 AI **一起**进池 | AI 桶 2→24 个 ⇒ `bosses_home_generic` / `all_bosses_shoreline` 出档率被稀释 ≈92% —— 正是「把别的活动挤出轮换」 |
| **C. 数据层把 4 个活动的日期窗改成 0** | 进池 | 会**废掉**它们自己的日期窗自动开启（例如 `scourge_incursion` 10/16~10/26 的官方窗口），属行为回退 |
| **D. `alwaysInRotation` 数据开关（本次采用）** | 只多 1 个候选 | 影响面 = 数据里显式标注的活动；空池规则不变（新活动以后照样自动进池）；DLL + events.json 走既有部署链，**不碰用户 config** |

语义边界（`EventDef.cs:24-54`、`Rotation.cs:197-216`）：
1. 只影响**轮换候选资格**，**不改**日期窗自动开启（两边独立）；
2. `seasonal` 活动**永远**不受它影响（`!IsSeasonal(e)` 在分支最前面短路）；
3. 只在 `rotation.pool` **为空**时参与（池子非空以白名单为准）。
4. ⚠ 显式标注 = **不论 `seasonRotation.mode` 是 `rotate` 还是 `fixed`** 都在池里
   （3 个 `event_task` 也因此从「只有 rotate 才进池」变成「一直进池」——这就是「加进轮换」的语义）。

## 7. 对老活动的影响评估（诚实版）

1. **16 个老 `event_task` + 5 个 `reward`：出档次数逐字不变**（自检里是一条硬断言：
   「365 档：老『带任务 / 奖励』活动出档次数逐字不变」）。因为加进去的只有 AI 桶，
   `tasks`/`rewards`/`smalls` 三个桶的成员与排序都没变。
2. **2 个老 AI 活动被「稀释」而不是被「踢掉」**：AI 档总数不变（365 档里 AI 档 183 档），
   而且**这 3 个 AI 活动两两互斥**（都动储备站的 `bossGluhar` 等同一批「同图同首领」，
   探针里可复算）⇒ 每个 AI 档最终只开 1 个 AI ⇒ 总 AI 出档 183 次**前后一致**，
   只是从 2 个成员分（102/81）变成 3 个成员分（71/56/56）⇒ 各自 −31%。
   **没有任何活动的出档次数变成 0**。这是「往 AI 桶里加一个成员」的**必然代价**，不是规则被改坏。
3. **带任务 ≤1 / AI×带任务互斥 / 活动 1~2 + 奖励 1~2**：改动前后 365 档各 0 违规（探针【5】）。
4. **4 个新活动彼此不冲突**（探针【6】打印），但硬互斥仍保证「AI 类（八影会谈）与带任务类（另 3 个）不会同档」。
5. 若用户**不接受** AI 老活动被稀释：把 `meeting_of_the_bosses_2026` 的 `alwaysInRotation` 删掉即可
   （1 行数据回滚，其它 3 个本来就在池里，行为回到今天）。
