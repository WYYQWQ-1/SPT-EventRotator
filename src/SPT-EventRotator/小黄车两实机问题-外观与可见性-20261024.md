## 1. 问题 1：自造物品外观（海报 → 武器箱）

### 1.1 三个候选 tpl 的实机事实（`SPT_Data/database/templates/items.json` 只读）

| tpl | `_name` | `_parent` | W×H | `_props.Grids` | `_props.Prefab.path` |
|---|---|---|---|---|---|
| `59fb023c86f7746d0d4b423c` | `item_container_weaponcase`（Weapon case） | `5795f317245977243854e041` | **5×2** | `main 5×10`（非空 ⇒ 容器类） | `assets/content/items/containers/item_container_weaponcase/item_container_weaponcase.bundle` |
| `5909d7cf86f77470ee57d75a` | `terraWBoxSquare` | `566965d44bdc2d814c8b4571` | 1×1 | `main 4×4`（非空） | **`""`（空字符串）** |
| `675a081c1474133a0d0bb214` | `item_barter_flyers_strange_case`（旧用的那件） | `6759673c76e93d8eb20b2080` | 2×2 | 空 | `…/barter/item_barter_flyers/item_barter_flyers_strange_case.bundle` |

### 1.2 根因（有铁证）

旧 `Prefab` 逐字等于 `item_barter_flyers_strange_case.bundle`，而它主人的本体 locale 名字是：

```
675a081c1474133a0d0bb214  Name = "Things Sure Are Strange poster"   ShortName = "Poster"
59fb023c86f7746d0d4b423c  Name = "Weapon case"                     ShortName = "Weapons"
5909d7cf86f77470ee57d75a  Name = "Weapon box"                      ShortName = "Weapon box"
```

（`SPT_Data/database/locales/global/en.json` 只读）

⇒ 上一版把**一张海报（Poster）**当成了"2×2 箱子"。当时的理由写的是
"该 tpl 在 12 张图的原版 looseLoot 里出现 ⇒ 已被证明能当 loose loot 正常落地"——
这句话**只证明它会落地，不证明它是个箱子**。玩家在车旁看到的"海报"不是贴图/渲染 bug，
是**选了个名字里就写着 poster 的资产**。

### 1.3 改成了什么

```json
"Prefab": { "path": "assets/content/items/containers/item_container_weaponcase/item_container_weaponcase.bundle", "rcid": "" }
```

来源 = 原版武器箱 `59fb023c86f7746d0d4b423c` 的 `Prefab` 字段，**逐字照抄**（探针断言字符串相等，不是"包含"）。
本体共 **54** 个 tpl 共用这个 bundle（`59fb023c` + 53 个空投箱 `event_container_airdrop_*` 等），
所以这个 bundle 一定是客户端真实存在、且能当"地上战利品"渲染的资产。

> **`5909d7cf86f77470ee57d75a` 不能用**：它是地图静态木箱（`terraWBoxSquare`），
> `_props.Prefab.path` 是**空字符串** —— 服务端这条 tpl 没有 prefab，模型的显示由客户端场景对象决定。
> 所以"用它或 `59fb023c` 的 Prefab"实际只有**一个**可选项。

### 1.4 尺寸为什么是 3×2（不是 5×2）

原版武器箱本体是 **5×2**。但 5 宽**塞不进 4×4 口袋**（旋转成 2×5 也不行，5 > 4），
玩家没背包就走过去**捡不起来**——这对一个"走过去拿箱子"的寻物任务是不能接受的。
⇒ 取你要求的 **3×2**（能进 4×4 口袋），模型仍是武器箱（模型尺寸由 bundle 决定，不受 `Width/Height` 缩放）。

⚠ 如实记：所以"格子 3×2 / 模型 5×2"是不一致的（模型比格子宽 2 格）。若要严格一致就写 5×2，
代价是必须带背包。**要不要换 5×2 由你拍板**，一个字段的事。

### 1.5 Grids

`_props.Grids` 写成 **`[]`**（不是省略）。依据：客户端按 `_type`/`Template.Type` 决定 Item 子类
（`ItemFactory` 的 `method_10`→`Flyer`、`method_15`→`CompoundItem` 那张映射表），**不是**按 `Grids` 决定；
所以 `Grids: []` 不会把它变成 CompoundItem/容器，只让"非容器"这件事在数据上显式化、也顺手让
`LooseLootInjectDimension` 的容器类诊断（`Grids` 非空 ⇒ warning）不再命中。

### 2.3 真因（按影响排序）

1. **主因：模型错了**（§1）。刷出来的确实是传单箱，躺在地上像一堆纸 —— 玩家"看不到箱子"。
2. **次因：点位是概率刷的**。那 2 个点 `probability` 只有 0.437 / 0.411，而
   `num = round(interchange LooseLootMultiplier 2.8 × Normal(621.244, 18.379)) ≈ 1739`
   要从 3820 个点里抽（`Σp = 578.03`，`ProbabilityObjectArray.DrawAndRemove` 加权无放回）
   ⇒ 单点落地率 ≈ `1 - exp(-1739 × 0.437 / 578.03) ≈ 73%` / 另一 ≈71%
   ⇒ **那次跑过去一件都没有 ≈ 8%**。8% 不算主因，但对一条寻物任务的关键道具不该留空白。
3. `IsContainer` / 客户端分支：我们替换后刷点仍是 `IsContainer=false`，走普通 `SpawnLootItem` 路径，
   不进"按静态容器 Id 匹配"的分支 ⇒ **不是原因**（这条以前猜过，现在有结论了）。

## 3. 兜底方案（车旁 append 静态容器）：**做不到**，不是"以后再说"

实测（实机 `user/mods/ManimalInterchange/db/locations/interchange/staticContainers.json` 只读）：

* **906** 个静态容器，**Position 全是 (0,0,0)**（非零 0 个）；`Id` 全是场景实例名 `Lootable_00000…`（唯一 906 个）。
* `statics.json`（同目录）只有 `containers{Id → groupId}` + `containersGroups`，**没有任何坐标**。

客户端 `SpawnLoot`（`Assembly-CSharp.decompiled.cs:552171-552231`）对 `IsContainer` 刷点：

```csharp
if (lootItem2.IsContainer) {
    IStaticLoot staticLoot = array2.FirstOrDefault(x => x.Id == lootId);   // array2 = 场景里的 StaticLoot/LootableContainer/StationaryWeapon
    if (staticLoot == null) { Debug.LogError(lootId + " is missing"); }
    continue;
}
```

⇒ 静态容器的**位置和模型来自客户端场景对象**，服务端 JSON 只是"往这个场景对象里塞东西"。
凭空 append 一条 `staticContainers`（哪怕写了车的坐标）在场景里没有对应对象 ⇒ 客户端只会打
`<id> is missing` 然后**什么都不生成**。
⇒ 想"在车旁多一个能开的箱子"必须改**客户端地图资产**（Unity 场景），不在本 mod 的服务端能力范围内。

**顺带排除**：也没法"注入到车旁最近的既有静态容器"——906 条记录里没有坐标，离线无法判断哪个容器在车旁。
所以"特定地点放一个特定任务物品"这条路，**loose loot 是唯一可行的那条**。

（若实机仍然看不到，下一步不是换容器，而是：把客户端 `Logs/log_*/errors.log` 里
`Item deserialization error` / `Could not add` / `lootId is missing` 任一行发过来 —— 那就说明是渲染/资产问题，不是数据问题。）

## 6. 2026-10-24 补记（**推翻** §4 第 4 条的 `QuestItem != true` 结论）

> 起因：实机反馈「箱子能捡、但进不了任务物品栏（任务物品 → 任务物品栏（带入战局）为空）」。

**结论：必须 `_props.QuestItem = true`；上一轮"标了 QuestItem 地上就不出"是误读。**

反编译证据（`audit/client_full/Assembly-CSharp.decompiled.cs`）：

1. `GameWorld.GetQuestLootReady`（:552111-552126）：把 `location.Loot` 里 `Item.QuestItem == true` 的条目
   挪进 `_questLootItems`，其余照常 `SpawnLoot` ⇒ **刷点不会被删，只是换一条路**。
   这个列表同时覆盖 **loose loot 与 `IsContainer=true` 的静态容器条目**（`SpawnLoot` :552171 起按
   `lootItem2.IsContainer` 分流），判定条件只有模板 `_props.QuestItem`，**没有白名单/豁免字段**。
2. `GameWorld.ManageQuestLoot`（:552855-552895）：逐件复活 `_questLootItems`——玩家任务物品栏已有同 tpl ⇒ 跳过；
   否则在**状态 Started 的任务的 `AvailableForFinish`** 里找 `ConditionFindItem`，目标命中且未完成 ⇒
   `ValidProfiles=[该玩家]` 后 `SpawnLootItem(..., initial:true, player)`（`SpawnLootItem` :552329，落点是原刷点坐标）。
3. `LootItem.Init`（:916089）：`item.QuestItem` 时 `SetActive(validProfiles != null && 当前 profile ∈ validProfiles)`
   ⇒ 没有匹配任务时 `ValidProfiles=null`（:552888）⇒ 物体隐藏。**这就是"没接任务看不见"的原因，是官方任务物品行为。**
4. 进任务物品栏：`ItemManipulator.QuickFindAppropriatePlace`（:856644-856650）对 `item.QuestItem` 直接
   `FindQuestGridToPickUp`：战局内 → `QuestRaidItems.Grid`（:848844；UI 名"任务物品栏（带入战局）"），
